Contrato do desafio · NO IA

O código precisa sair da sua cabeça e das suas mãos.

O objetivo não é terminar o CRUD o mais rápido possível. É conseguir construir, errar, investigar e corrigir sem terceirizar o raciocínio para uma IA. Durante as fases do desafio, IA não é ferramenta de programação: é resposta pronta demais.

PROIBIDO DURANTE O DESAFIO

  • Pedir código para IA. Nada de “crie o método salvar”, “faça meu CRUD”, “implemente esse repository” ou equivalentes.
  • Pedir para completar código. Não enviar um método pela metade para ChatGPT, Gemini, Claude ou outra IA terminar.
  • Pedir correção automática. Não colar sua classe e perguntar “o que está errado?” esperando que a IA encontre e entregue a correção.
  • Colar stack trace para IA resolver. O erro deve ser investigado por você usando a mensagem, debugger, documentação e busca tradicional.
  • Usar geração de código da IDE. GitHub Copilot, Cursor, JetBrains AI, IntelliCode generativo e recursos equivalentes devem ficar desligados.
  • Aceitar autocomplete gerado por IA. Autocomplete normal da IDE é permitido; sugestões que geram blocos inteiros por IA, não.
  • Pedir algoritmo ou lógica pronta. Mesmo sem código: “qual lógica uso para atualizar por id?” já entrega a parte que você precisa exercitar.
  • Pedir testes prontos. Casos de teste e código de teste também fazem parte do raciocínio do desafio.
  • Copiar solução completa de tutorial. Tutorial pode explicar um conceito; não vale reproduzir um CRUD equivalente linha por linha.

USE ISTO NO LUGAR

  • Documentação oficial. Java Docs, Spring Docs, MDN, TypeScript Docs, React Docs e documentação do MySQL.
  • Autocomplete tradicional da IDE. Nomes de métodos, imports, assinaturas e navegação de API são consulta, não raciocínio terceirizado.
  • Debugger. Breakpoints, inspeção de variáveis e execução passo a passo devem ser sua principal ferramenta quando “não faz sentido”.
  • Mensagem de erro. Leia inteira. Identifique classe, linha, exceção e causa antes de pesquisar qualquer coisa.
  • Busca tradicional. Pesquise a mensagem de erro ou um conceito específico em mecanismos de busca, Stack Overflow e fóruns.
  • Exemplos pequenos de documentação. Pode consultar como usar ArrayList.remove, Optional, uma annotation ou uma API isolada — depois adapte sozinho.
  • JavaDoc / “Go to definition”. Abra a implementação, assinatura ou documentação da biblioteca para entender o que o método espera e retorna.
  • Papel, pseudocódigo e desenho. Antes de codar, escreva com suas palavras: entrada → regra → saída.
  • Pedir ajuda humana conceitual. Vale discutir o conceito sem receber a implementação do seu desafio.

QUANDO TRAVAR: protocolo obrigatório antes de procurar uma solução

01 · LERLeia o erro e encontre exatamente a linha onde o comportamento quebra.
02 · HIPÓTESEEscreva o que você acha que deveria acontecer e o que aconteceu de fato.
03 · INVESTIGARUse debugger, documentação e buscas por conceitos ou mensagens específicas.
04 · TESTARFaça uma alteração pequena por vez e confirme se sua hipótese estava certa.
Regra de ouro: se a ferramenta pensou a solução específica do desafio por você, não vale. Se ela apenas forneceu documentação, referência de API ou informação para você raciocinar, vale.

Duas trilhas, mesma lógica

Cada trilha tem 3 estágios em cascata. Cada estágio traz objetivo, estrutura mínima e critérios de aceite. Você só avança quando cumprir os critérios e conseguir explicar, por escrito, o que mudou e por quê.

Trilha 01

Java

Console → Spring Boot + JPA → API REST

Puro

CRUD no console, em memória

Objetivo: construir o CRUD inteiro sem framework para entender, na prática, a responsabilidade de cada camada antes de usar Spring.

Estrutura mínima
  • model/Produto.java
  • repository/ProdutoRepository.java
  • service/ProdutoService.java
  • exception/PrecoNegativoException.java
  • exception/ProdutoNaoEncontradoException.java
  • view/ProdutoMenu.java e Main.java
Produto — atributos
  • Long id — identificador único
  • String nome — obrigatório e não vazio
  • double preco — não pode ser negativo
  • int estoque — quantidade disponível
Repository — métodos esperados
  • salvar(Produto produto)
  • listarTodos()
  • buscarPorId(Long id)
  • atualizar(Produto produto)
  • deletar(Long id)
Service — regras de negócio
  • Validar preço antes de cadastrar ou atualizar.
  • Impedir nome vazio.
  • Não deixar o menu acessar a List diretamente.
  • Lançar exceção quando o produto solicitado não existir.
Critérios de aceite
  • É possível cadastrar, listar, buscar, atualizar e excluir produtos pelo console.
  • Os dados permanecem enquanto a aplicação estiver executando.
  • Preço negativo gera PrecoNegativoException.
  • ID inexistente em busca, atualização ou exclusão gera ProdutoNaoEncontradoException.
  • ProdutoMenu apenas coleta/exibe dados e chama o service.
  • ProdutoRepository é a única classe que manipula a List<Produto>.
  • Ao encerrar e abrir novamente, os dados somem — isso é esperado nesta fase.
~1 semana
Framework

Spring Boot + JPA + banco real

Objetivo: trocar apenas a infraestrutura de persistência: sair da List e gravar os mesmos produtos em um banco real com Spring Data JPA.

Dependências e configuração
  • Spring Boot, Spring Data JPA e driver MySQL.
  • application.properties ou application.yml com conexão do banco.
  • Banco e tabela criados/gerenciados para persistir Produto.
Produto — entidade JPA
  • Adicionar @Entity.
  • id com @Id e geração automática.
  • Manter nome, preco e estoque.
  • Construtor vazio exigido pelo JPA.
Repository
  • Substituir a classe manual por uma interface.
  • ProdutoRepository extends JpaRepository<Produto, Long>.
  • Remover a List<Produto> e os métodos CRUD escritos manualmente.
Service — métodos esperados
  • cadastrar(Produto produto)
  • listarTodos()
  • buscarPorId(Long id)
  • atualizar(Long id, Produto produto)
  • deletar(Long id)
Critérios de aceite
  • O CRUD continua funcionando sem acessar diretamente o banco.
  • Os produtos permanecem salvos após reiniciar a aplicação.
  • O ID é gerado pelo banco/JPA, não digitado manualmente.
  • As mesmas validações e exceções da fase anterior continuam válidas.
  • O comportamento é demonstrado por um CommandLineRunner, ainda sem HTTP.
  • Você consegue explicar qual código manual deixou de existir graças ao JpaRepository.
~1 semana
API

Exposição via REST

Objetivo: expor o CRUD por HTTP sem misturar entidade, regra de negócio e detalhes de resposta da API.

Estrutura nova
  • controller/ProdutoController.java
  • dto/ProdutoRequest.java e dto/ProdutoResponse.java
  • exception/GlobalExceptionHandler.java
Endpoints obrigatórios
  • POST /produtos — cadastrar
  • GET /produtos — listar todos
  • GET /produtos/{id} — buscar por ID
  • PUT /produtos/{id} — atualizar
  • DELETE /produtos/{id} — excluir
Responsabilidades
  • Controller recebe HTTP e chama o service.
  • Service mantém as regras de negócio.
  • Repository continua responsável pela persistência.
  • DTO define o formato de entrada e saída da API.
Critérios de aceite
  • POST válido retorna 201 Created.
  • GET válido retorna 200 OK.
  • DELETE válido retorna 204 No Content.
  • ID inexistente retorna 404 Not Found.
  • Dados inválidos retornam 400 Bad Request.
  • Exceções conhecidas são tratadas pelo @ControllerAdvice; não viram 500 genérico.
  • A entidade JPA não é usada diretamente como contrato público da API.
  • Os cinco endpoints podem ser testados por Postman, Insomnia ou curl.
~1 semana
Trilha 02

TypeScript · HTML · CSS

DOM puro → React → consumindo a API Java

Puro

CRUD manipulando o DOM na mão

Objetivo: reproduzir o mesmo CRUD no navegador manipulando estado e DOM manualmente, antes de usar React.

Produto — interface
  • id: number
  • nome: string
  • preco: number
  • estoque: number
Funções mínimas
  • adicionarProduto()
  • renderizarProdutos()
  • buscarProduto()
  • atualizarProduto()
  • removerProduto()
Critérios de aceite
  • CRUD completo usando um array em memória.
  • DOM atualizado sem recarregar a página.
  • Eventos registrados com addEventListener.
  • Validações aparecem na página, sem alert().
  • Nenhum any usado para contornar tipagem.
  • Refresh apaga os dados, como esperado nesta fase.
~1 semana
Framework

Componentização com React

Objetivo: trocar a manipulação direta do DOM por componentes e estado declarativo, mantendo o CRUD ainda em memória.

Componentes esperados
  • ProdutoForm
  • ProdutoTable
  • ProdutoRow ou equivalente
Critérios de aceite
  • Estado de produtos controlado com React.
  • Cadastro, edição e exclusão atualizam a interface automaticamente.
  • Nenhum querySelector usado para controlar linhas da tabela.
  • A interface Produto continua tipando os dados.
  • Você consegue explicar o que o React passou a fazer no seu lugar.
3-4 dias
API

Consumindo a API Java de verdade

Objetivo: remover a fonte de dados local e fazer o front React depender da API Java construída na trilha anterior.

Integração esperada
  • GET /produtos ao carregar a tela.
  • POST ao cadastrar.
  • PUT ao editar.
  • DELETE ao excluir.
Critérios de aceite
  • Operações HTTP usam fetch() + async/await.
  • Existe estado de carregamento.
  • Falha da API gera mensagem amigável na tela.
  • CORS está configurado e documentado.
  • Após atualizar o navegador, os produtos continuam aparecendo porque vêm do MySQL.
  • O array local não é mais a fonte oficial dos dados.
~1 semana
onde as trilhas se encontram

O produto criado no formulário React sobrevive a um refresh — porque agora mora no MySQL, atrás da sua API Spring.

É o único ponto do desafio onde as duas trilhas precisam concordar: o front fala com o back por HTTP, e o navegador vai reclamar de CORS na primeira tentativa. Resolver isso é parte do critério de conclusão.
